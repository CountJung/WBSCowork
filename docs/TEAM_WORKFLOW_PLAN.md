## 제품 목표

사용자가 설명한 목표는 **주어진 주제를 업무 카드로 나누고, 구성원에게 각자의 파트를 배정하여, 수행한 결과물을 제출·공유하는 것**이다. 여기에 완료 기준과 피드백을 연결하면 팀이 “다음에 누가 무엇을 해야 하는지” 알 수 있다.

기존 `project`를 주제/업무 묶음, `task.parent_id`를 세부 업무 분해에 활용하는 안을 기본으로 한다. 별도의 주제 계층이나 새 게시판을 추가하는 것은 현재 목표에 필요하지 않다. 자동 생성·AI 배정은 요청된 필수 기능으로 간주하지 않는다.

## 우선순위와 범위

1. **먼저 진입과 의미를 바로잡는다.** 일반 팀원의 프로젝트 전환(PRD-033), 목표·완료 기준(PRD-034), 수행 가능한 담당자와 책임 정책(PRD-035), 실제 업무 상태·진척(PRD-036). 일정 경과를 완료율로 오해하지 않게 한다.
2. **제출과 완료 사이를 연결한다.** 원본이 남는 제출 버전(PRD-037) → 보완 요청/재제출/승인(PRD-038) → 내 업무·검토 대기(PRD-039). 모든 카드에 검토자를 강제하기보다 “검토 필요” 여부를 명시하고 완료 권한을 구분한다.
3. **팀 운영을 편하게 한다.** 주제 현황·차단/선후행(PRD-040), 수동 템플릿(PRD-041), 권한을 지키는 검색(PRD-042), 필요한 인앱 알림(PRD-043). 복잡한 가중 진척·자동 일정 재조정·채팅 편집기·다단계 결재는 초기 범위에서 제외한다.
4. **한 흐름으로 검증한다.** PRD-044는 새로운 화면 수가 아니라 실제 협업 한 사이클을 완료 조건으로 둔다. 기존 보안 유지보수(OPS-032)와 권한/저장소 회귀는 병행 게이트다.

## 구현 전에 확정할 정책

- **협업 범위:** 한 조직 전체가 함께 보는 현재 공개 범위를 유지할지, 프로젝트 참여자 범위를 추가할지 정한다. 현재 `public`은 모든 인증 사용자, `private`은 작성자+admin/SU다. 이번 계획만으로 기존 비공개 제출물을 공동 담당자/검토자에게 공개하지 않는다.
- **역할:** 앱의 guest/member/admin/SU와 카드 주담당/기여자/검토자는 다른 개념이다. 카드 배정만으로 앱 역할이 승급하지 않는다. 우선 주담당 1명+사람별 하위 카드로 책임을 분명히 하고, 복수 기여자가 필요한 카드만 명시적으로 지원한다.
- **완료:** 검토 필요한 카드는 승인된 제출 버전에 근거하여 완료한다. 검토 불필요 카드는 정해진 담당자가 완료 근거를 남긴다. 자체 승인 허용 여부, 승인 취소·재오픈 사유와 권한을 문서화한다.
- **보존:** 이전 제출본과 검토 이력의 보존 기간/삭제·복구 규칙을 정한다. 기존 비공개 R2 권한과 실패 정리 절차를 재사용하며, 제품 데이터의 영구 삭제와 외부 전송은 별도 권한 범위를 따른다.

## 팀 업무 인수 시나리오

예: “신제품 소개 자료 준비” 프로젝트에 조사·초안·검토 카드 3개를 만들고 구성원 2명에게 각자의 카드를 배정한다.

1. 일반 팀원이 화면에서 해당 프로젝트로 전환하고 내 업무에서 담당 카드, 기한, 기대 산출물, 완료 기준을 확인한다.
2. 작성자가 파일 1개와 자료 링크를 포함한 v1을 제출한다. 파일만/링크만/혼합 제출 중 지원하는 형식의 검증 규칙이 명확하다.
3. 조회·검토 권한이 있는 검토자에게 대기가 표시되고, 보완 요청에 사유를 남긴다. 작성자는 요청된 수정을 내 업무에서 확인한다.
4. v2를 재제출해도 v1과 당시 피드백이 남는다. v2를 승인하면 승인 대상·수행자·시각이 기록되고, v1의 승인이 v2에 자동 이전되지 않는다.
5. 프로젝트 현황에 남은 업무·차단·검토 대기가 실제 상태와 일치한다. 날짜가 지났다는 이유만으로 완료가 늘지 않는다.
6. 다른 계정의 비공개 파일, 직접 링크, 검색 건수, 알림 요약에서 정보가 새지 않는다. 반복 제출·동시 검토·세션 만료/중단 후 복귀에서도 중복 승인이나 원본 손실이 없다.

검증은 합성 자료로 수행하고 실사용자 역할 변경·비밀정보·외부 발송을 포함하지 않는다. Google 로그인과 기존 업무/첨부 권한을 유지한다.


## P0 구현 기본 계약 (2026-10-09)

사용자의 P0 전체 진행 요청에 따라 PRD-033~039/044를 구현한다. 기존 공개 범위와 Google 역할을 유지하고 아래 보수적 기본값을 사용한다.

- 프로젝트 참여자 모델이나 private 공유 권한을 새로 부여하지 않는다. 담당자는 member/admin 또는 유효한 SU이며 기존 guest 배정은 자동 삭제/승급하지 않고 수행 불가를 표시한다.
- 주담당 1명과 사람별 하위 카드를 사용한다. 기존 카드 편집 권한과 실행/검토/완료 권한을 구분하고 재배정 이력을 보존한다.
- 검토는 선택사항이다. 지정 검토자는 현재 해당 버전을 볼 수 있고 작업 가능한 역할이어야 한다. author/assignee/해당 버전 작성자의 자체 승인은 admin/SU도 거부한다.
- 검토 없는 완료는 권한 있는 담당자/관리자가 근거를 남긴다. 검토 필요 카드는 특정 제출 버전의 승인 없이 직접 완료할 수 없다. 재오픈은 사유를 남기고 이전 승인 이력은 보존한다.
- 기존 자료는 현재 남은 원문/파일만 첫 버전으로 보존한다. 과거 덮어쓴 자료는 복원됐다고 표시하지 않고 기존 댓글은 버전 미지정으로 구분한다. 버전은 자동 만료/삭제하지 않는다.
- 이전 버전 조회·첨부는 현재 제출물과 버전 당시 공개 범위를 모두 적용한다. 검토자/담당자 지정이나 현재 private→public 변경으로 과거 비공개 내용을 공개하지 않는다.
- 전체 완료 수는 말단 업무를 기준으로 하고 묶음 카드 수를 별도로 보여 준다. 날짜 경과율을 완료율로 사용하거나 WBS 부모 관계를 선후행 화살표로 표시하지 않는다.
- 프로젝트/자료 영구 파기는 별도 기존 확인 절차이며 이번 기능 구현 중 운영 자료를 삭제하지 않는다. 새로운 보존 기간/휴지통 정책은 추가하지 않는다.

PRD-033의 첫 Worker 계약187개는 두 프로젝트와 5역할의 서버 렌더링/직접 링크를 검사한다. 브라우저 Back/Forward·모바일과 전체 제품 흐름은 PRD-044에서 별도 확인하며 HTTP 반복 요청을 브라우저 검증으로 계산하지 않는다.

### 실행 상태 구현 계약 (PRD-035/036)

- 모든 인증 사용자의 기존 프로젝트/task 공개 범위를 유지한다. private 제출물은 작성자/admin/SU만 본다. 담당/검토자 배정은 접근 권한을 추가하지 않는다.
- 카드 편집·재배정은 기존 member/admin/SU 권한, 실행 상태는 현재 담당자/admin/SU 권한이다. 현재 쓰기할 수 없는 사용자를 새 담당/검토자로 선택할 수 없고 기존 guest 배정은 표시하여 재배정을 유도한다.
- planned/in_progress/blocked/review_pending/changes_requested/done을 사용한다. 검토 상태는 제출물 검토 절차 전용이다. 시작 뒤 reviewRequired를 바꾸지 못하고 no-review 완료에는 기준·실제 담당자 제출·완료 근거가 필요하다. 재개/차단 사유는 모든 인증 사용자에게 보이는 업무 metadata임을 입력란에서 안내한다.
- 생성/변경 이력은 운영 로그와 별도이며 token/version으로 원자적 중복/경합을 처리한다. 이전 task의 현재 상태 baseline은 이력 도입 시점이라고 명시한다. 카드 UI의 이력은 최근10건이고 전체 이력은 저장한다.
- 간트는 leaf 완료를 집계하고 컨테이너를 분모에 더하지 않는다. 부모 관계는 선행조건이 아니다. 실제 review 승인은 PRD-038에서 특정 제출 버전에 결합한다.

### 산출물 버전 구현 계약 (PRD-037)

- 제출의 본문·공개 범위·자료 링크·이전 파일은 새 버전으로 보존한다. 수정은 변경 요약과 현재 버전이 필요하며, 본래 작성자와 실제 편집자를 구분한다. HTTP(S) 링크만 허용하고 서버가 링크를 가져오지 않는다.
- 현재 버전에서 첨부를 제외해도 이전 버전의 파일을 지우지 않는다. 원래 작성자/admin/SU만 수정하고, 조회·댓글·첨부는 현재 제출물과 당시 버전의 공개 범위를 SQL에서 함께 검사한다.
- 기존 자료는 남아 있는 본문/파일을 이력 도입 시점의 snapshot으로 표시한다. 기존 댓글은 버전 미지정이고 과거 편집자/시각을 추측하지 않는다. `/submissions/[id]`에서 허용된 버전·첨부·댓글·이력을 조회한다.
- 업로드 후 metadata는 같은 transaction에 snapshot·첨부·이력을 기록한다. 반복 토큰은 실제 파일 bytes hash와 비교하고 새로운 임시 파일만 정리한다. R2 staging expiry와 cleanup 재시도 시각을 분리하며 만료/회수한 upload 권한은 backoff로 되살리지 않는다. 정리는 원본·첨부·모든 snapshot의 참조를 검사한다.
- 버전은 자동 삭제하지 않는다. task/submission 전체 영구 삭제에는 이전 버전과 파일이 함께 제거됨을 명시 확인하고, 프로젝트 파기는 기존 관리자 확인을 유지한다. 이번 P0 작업에서 운영 영구 삭제를 실행하지 않는다.
