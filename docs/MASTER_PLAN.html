1. 제품 목표와 원칙

WBSCowork는 게시판이 아니라 프로젝트의 WBS 태스크에 일정, 산출물, 첨부, 피드백을 귀속시키는 협업 시스템이다.

태스크 중심

프로젝트 기간과 계층형 태스크를 Gantt 및 집중 라우팅으로 연결한다.

산출물 중심

Markdown 제출물, 공개/비공개, 다중 첨부와 댓글을 하나의 가시성 경계로 취급한다.

운영 가능성

env readiness, APP_PORT, MariaDB 검사, 파일/롤링 로그를 실제 하네스로 관리한다.

점진적 진화

기능 변경과 구조 이동을 분리하고 URL·SQL·권한 계약을 보존한다.

3. 목표 구조와 데이터 흐름

Browser → root app adapters → widgets/features → entities/repositories → MariaDB · UPLOAD_DIR · LOG_DIR

FSD 계약

루트 app/는 유지한다. 의존 방향은 app → widgets → features → entities → shared, 구현/이동 순서는 shared → entities → features → widgets → app다. server-only DB/env/fs는 client graph에 들어가지 않는다.

현재 데이터 관계

projects 1──N tasks (self parent, nullable assignee)
tasks 1──N submissions
submissions 1──N comments
submissions 1──N submission_attachments
users 1──N assigned tasks / submissions / comments

project membership, owner, task 상태/진척률, migration ledger, digest/report tables는 현재 없다. 없는 데이터를 제품 사실처럼 표현하지 않는다.

4. 권한·가시성 우선 계획

역할읽기쓰기/운영
guestpublic 제출물읽기 전용
memberpublic + 본인 private태스크/제출물/댓글/첨부 쓰기
admin모든 제출물관리 개요·프로젝트·사용자, guest/member 부여
superuser모든 제출물DB/로그/설정 포함 전체, admin 부여

P0 · 파생 데이터 누출

작업 page의 comment/attachment project 조회가 submission visibility filter와 결합되지 않고, 그 결과 전체가 client component props로 전달된다.

P1 · mutation ownership

제출물·댓글 update/delete action이 쓰기 역할만 검사한다. 타인의 private 제출물을 수정하거나 public으로 바꾸는 경로가 열려 있다.

확인됨 · 직접 다운로드

두 attachment GET handler는 부모 제출물 가시성을 검사하고 unauthorized/missing을 모두 404로 응답한다.

불변조건: private 제출물의 본문, 댓글, 첨부 metadata, binary, 수정/삭제 경로는 모두 동일한 actor-aware 정책을 통과한다. UI 사후 필터는 보안 경계가 아니다.

5. 실행 로드맵

P0

기밀성 기준선

  • viewer-aware submission 단건/목록 정책을 단일화한다.
  • comment/attachment query를 부모 visibility에 결합하고 client 로 넘기는 payload를 가시 제출물로 좁힌다.
  • guest/member/admin/superuser 및 교차 ID fixture를 만들고 focused test script를 실제 추가한다.
P1

인가·무결성

  • 모든 Server Action의 target project/task/submission 관계와 author ownership을 감사한다.
  • DB cascade와 파일 삭제 실패의 일관성/복구 전략을 정한다.
  • 로그에서 secret, private body, raw file path를 redaction한다.
P2

FSD 유지

  • FSD M0~M5 완료 구조를 유지하고 새 코드는 public API 경계를 따른다.
  • shared, entities, features, widgets, root app adapter 의존 방향을 `npm run check:fsd`로 검증한다.
  • 기능 변경과 구조 이동을 한 변경에 섞지 않는다.
P3

DB 운영 성숙도

  • versioned migration/ledger와 fresh/existing/rollback 절차를 도입한다.
  • runtime CRUD credential과 schema admin credential을 분리한다.
  • 대표 데이터의 index/EXPLAIN 및 backup/restore runbook을 검증한다.
P4

Synology/NAS 배포

  • Node/MariaDB, persistent upload/log 경로, owner/mode, free space를 확정한다.
  • build/start health, reverse proxy TLS, OAuth callback URL, restart/rollback을 smoke test한다.
  • digest/report는 기존 설계의 D0~D5를 별도 승인 순서로 진행한다.

  • 권한 변경은 role × resource × ownership × visibility matrix로 검증한다.
  • DB 변경은 빈 DB와 기존 DB를 모두 검증하고 실제 연결이 없으면 미실행 사유를 남긴다.
  • AppleDouble(._*)이나 기존 JS lint 이슈는 변경 유발 오류와 분리한다.

7. 운영 체크리스트

배포 전

  • lockfile 설치와 production build
  • env configured 여부(값 노출 금지)
  • DB 연결/managed schema
  • UPLOAD_DIR·LOG_DIR 쓰기/용량
  • OAuth callback·NEXTAUTH_URL

배포 후

  • /, /tasks, admin role smoke
  • public/private 및 직접 download
  • 업로드 크기/삭제/재시작
  • 로그 생성·retention
  • DB/file backup 복원 리허설

장애 시

  • 비밀값 없이 timestamp/route/actor role 기록
  • 앱, DB, 파일 저장소 경계 분리
  • 최근 배포 rollback과 schema 호환 확인
  • private 데이터 노출이면 즉시 P0 처리

8. 완료 정의

  1. 요구한 사용자 동작이 실제 route/action에서 작동한다.
  2. server-side 권한과 산출물 파생 데이터 가시성이 matrix를 통과한다.
  3. lint/build 및 변경 범위 하네스의 실제 결과가 기록된다.
  4. 스키마·repository·문서 설명이 일치한다.
  5. 기존 사용자 변경을 보존하고 최종 git 상태를 보고한다.
  6. 명시적 요청 없이는 commit/push하지 않는다.
